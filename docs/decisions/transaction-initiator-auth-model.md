# 거래 개시 주체별 인증·인가 모델 — 설계 결정 기록

> 이 결정은 C1(Loan ↔ Ledger 회계 경계)에서 촉발됐지만 **C1에 국한되지 않는다.**
> 여신·수신·결제·고객·에이전트의 권한 경계를 정할 때마다 "이 거래에 고객 인증을
> 붙여야 하나" 를 다시 결정하지 않기 위해, 상위 원칙으로 먼저 박는다.

## 문제 정의

이체 승인 게이트(`TransferApprovalGate`)를 켤 때 적용 대상 목록을 이렇게 적었다.

> 이 게이트를 지나는 경로는 **셋이고 전부 토큰을 보낸다** — 웹 내부이체,
> 웹 타행이체(결제계), 챗봇 이체. **자동이체 스케줄러는 컨트롤러를 거치지 않아
> 해당 없고**, 예약이체는 등록 시점에 확인한다.

**"자동이체 스케줄러는 컨트롤러를 거치지 않는다" 가 사실이 아니었다.**
`AutoDebitBatchService` 는 `PaymentServiceClient` 로 `POST /api/v1/payments`
(= 컨트롤러)를 탄다. 대출 실행·온라인 상환·역분개도 같다. 경로는 셋이 아니라
일곱이었고 넷이 누락됐다. 근거는 [`../plan/loan-payment-ledger-trace.md`](../plan/loan-payment-ledger-trace.md).

그 결과 두 가지가 동시에 일어났다.

1. **여신 자금이동 전체가 401 로 막혔다.** `TRANSFER_APPROVAL_REQUIRED` 기본값이
   `true` 이고, 여신은 고객 승인 토큰을 가질 수 없다.
2. **`X-Auth-Token-Id` 가 두 의미를 겸하게 됐다.** loan 은 이것을
   `payment_instruction.auth_token_id`(VARCHAR(20) UNIQUE 기술 식별자)로 채우려고
   멱등키를 SHA-256 해시해 만들고, core 는 같은 값을 고객 승인 토큰으로 읽어
   customer-service 에 검증하러 간다. 어느 쪽도 만족시킬 수 없다.

**이것은 헤더 하나의 문제가 아니다.** 고객이 개시한 거래와 시스템이 개시한 거래를
같은 인증 모델에 밀어 넣은 결과다.

## 원칙

아래 결정들은 이 다섯 문장에서 나온다. 개별 판단이 갈릴 때 여기로 돌아온다.

1. **Core Banking 을 최초의 내부 보안 경계로 설정한다.**
2. **게이트웨이의 사용자 인증에 의존하지 않고**, Core Banking 에서도 호출 주체의
   인증과 업무 권한을 검증한다.
3. 사용자 개시 거래와 시스템 개시 거래는 **서로 다른 인증 주체 모델**을 사용하되,
   **FDS·거래 정책·원장·감사 통제는 공통으로 적용한다.**
4. 서비스 권한은 **operation 단위로 최소 권한**을 부여하며, 권한 변경과
   authorization decision 은 감사 가능해야 한다.
5. 기존 WORM 감사 구조는 유지하고 **보안 이벤트를 감사 대상에 포함한다.**

> 원칙 1·2 는 현재 코드를 정면으로 부정한다. `payment/config/SecurityConfig` 는
> `anyRequest().permitAll()` 이고 주석은 "게이트웨이가 JWT 인증 → 백엔드는 통과" 다.
> **서비스 간 호출(동서)은 게이트웨이를 지나지 않으므로, 이 전제는 내부 호출에
> 적용되지 않는다.** 지금 core-banking 의 내부 호출에는 인증이 없다.

이 원칙이 논의의 단위를 바꾼다. C1 에서 여신을 손볼 때 물을 것은
"Loan 이 Payment 를 호출할 수 있느냐" 가 아니라
**"`LOAN_SERVICE` 가 어떤 payment operation 을 수행할 권한을 갖느냐"** 다.

## 결정

### 1. 개시 주체가 다르면 인증 모델이 다르다

```
                    CHANNEL / SYSTEM ACTOR
                           │
          ┌────────────────┴────────────────┐
          │                                 │
   Customer / Employee                Internal System
          │                                 │
          ▼                                 ▼
   Customer API                       Internal API
   /api/v1/payments                   /api/v1/internal/payments
          │                                 │
   사용자 인증                          서비스 인증
   + 고객 인가                          + 서비스 인가
   + Step-up / 거래 승인                + 거래 정책
          │                                 │
          └───────────────┬─────────────────┘
                          ▼
                     PAYMENT SERVICE
                          │
                    정책 / FDS / 멱등 / 감사
                          │
                          ▼
                     CORE BANKING
                          │
                          ▼
                        LEDGER
```

**핵심은 두 경로가 원장에서 만난다는 것이다.** API 경로는 분리하지만 거래 처리·원장
경계는 분리하지 않는다. 원장이 둘이 되면 이 문서를 쓴 이유가 사라진다.

### 2. 왜 시스템 거래에 step-up 을 요구하지 않는가

고객이 직접 지시한 거래는 이렇다.

```
고객 → "100만원 이체" → 본인 인증 → 거래 승인 → Payment
```

여신 자동상환은 이렇다.

```
대출 계약 → 약정 상환일 도래 → Loan 시스템 → 자동 집행
```

**후자에는 "본인이 이 거래를 지시했습니까" 라고 물을 본인이 없다.** 승인 시점은
계약 체결과 자동이체 등록이었다. 매 회차마다 다시 묻는 것은 인증 모델 자체가 맞지
않는다. 검증해야 할 것은 다른 질문이다 — **"이 거래를 실행할 권한이 있는 시스템인가."**

> **"internal API 라서 보안 검사를 생략한다" 가 아니다.**
> **"인증 주체가 사람에서 서비스로 바뀐다" 가 정확한 표현이다.**
> 이 구분을 흐리면 internal 경로가 통제 우회로가 된다.

### 3. `ROLE_INTERNAL` 하나로는 부족하다

```
/api/internal/**  →  ROLE_INTERNAL
```

여기까지만 하면 **내부 권한이 너무 넓다.** `ROLE_INTERNAL` 을 가진 서비스가 모든
내부 거래를 실행할 수 있게 된다. 서비스 계정은 사람 계정보다 오래 살고 회전이 적어,
권한이 넓으면 사고 시 영향 범위가 그만큼 넓다.

**호출자 신원과 수행 가능 작업을 분리한다.**

```
Loan Service
   │ service identity
   ▼
Internal Payment API
   ├─ authenticated service      누가 불렀는가
   ├─ authorized operation       무엇을 할 수 있는가
   ├─ allowed source = LOAN      어디서 온 거래인가
   ├─ allowed transaction        어떤 거래 종류인가
   ├─ amount policy              금액 한도
   ├─ account policy             허용 계좌
   ├─ idempotency                중복 방지
   └─ audit                      전건 기록
```

작업 어휘 예시:

```
LOAN_SERVICE
    ├─ LOAN_DISBURSE
    ├─ LOAN_REPAY_PRINCIPAL
    ├─ LOAN_REPAY_INTEREST
    └─ LOAN_REVERSE          ※ 아래 5 참조

CUSTOMER_CHANNEL
    ├─ TRANSFER
    └─ PAYMENT

EMPLOYEE_CHANNEL
    └─ OPERATIONAL_ACTION
```

### 3-1. 작업 권한의 정본은 DB 다

**권한 레지스트리(permission registry)를 DB 에 두고 그것을 정본으로 한다.**
코드에는 권한 **조회·검증**과 **거래 정책 실행** 로직만 둔다.

| 무엇 | 어디 |
|---|---|
| 어떤 서비스가 어떤 작업을 할 수 있는가 | **DB (정본)** |
| 금액·계좌·거래종류 정책 | **DB (정본)** |
| 권한을 조회하고 판정하는 코드 | 코드 |
| 정책을 실행하는 코드 | 코드 |

**코드 상수로 두지 않는 이유.** 권한을 바꾸려면 배포해야 하고, 그러면 "누가 언제 이
권한을 줬는가" 가 커밋 로그에만 남는다. 감독 검사에서 요구하는 것은 커밋 로그가 아니라
**권한 부여 이력**이다.

**설정 파일로 두지 않는 이유.** 같은 문제에 더해, 환경마다 갈라져 운영과 개발의 권한이
달라진다. 권한은 데이터지 배포 산출물이 아니다.

### 3-2. 두 종류의 감사를 남긴다

권한을 DB 에 두면 **감사가 두 겹**이 된다. 둘은 성격이 다르므로 따로 남긴다.

```
[1] 권한 부여·변경 감사      누가 언제 어떤 서비스에 어떤 작업 권한을 줬는가
      → 변경 이력. 드물게 일어나고 오래 보존한다.

[2] 인가 판정 감사           이 거래를 실행할 때 무엇을 근거로 허용/거절했는가
      → 거래마다 남는다. 거절도 남긴다.
```

**[2]에서 거절을 빼면 안 된다.** 권한 없는 서비스가 반복 호출한 흔적이 사라지면,
그것이 설정 실수인지 침해 시도인지 나중에 구분할 수 없다.

권한 레지스트리 자체도 감사 테이블과 같은 수준의 변경 통제를 받는다 —
`agent_audit_log` · `customer_access_log` 에 건 WORM 트리거와 같은 계열이다.

### 4. FDS 는 두 경로 모두 지난다

승인 게이트는 개시 주체에 따라 갈리지만 **이상거래 점검은 갈리지 않는다.**
자동이체도 이상거래 대상이다 — 오히려 사람이 보고 있지 않으므로 더 그렇다.
`FdsPreCheckGate` 는 internal 경로에도 적용한다.

### 5. 역분개는 실행과 같은 권한에 두지 않는다

`LOAN_REVERSE` 를 `LOAN_DISBURSE` 와 같은 권한 묶음에 두면, 한 서비스 신원이
자금을 내보내고 그 흔적을 되돌리는 일을 모두 할 수 있다. 업무분리(SoD) 원칙에
어긋난다.

당장 서비스를 쪼갤 필요는 없지만 **최소한 다음 둘은 지금 정한다.**

- 역분개는 별도 작업 권한으로 분리하고, 부여를 따로 기록한다
- 역분개는 사유(`reversal_reason`)와 행위자를 반드시 남긴다 — 원장 스키마에 이미 자리가 있다

### 5-1. 대출 실행은 자금이동이 아니다

> **대출 실행을 일반 자금이동으로 모델링하지 않고, 여신 도메인의 독립적인 거래 유형으로
> 취급한다. 대출채권과 고객예금의 생성은 단일 회계 거래로 원장에 기록하며,
> 집행계좌를 회계적 중간계정으로 사용하지 않는다.**

은행 회계에서 대출 실행은 돈을 옮기는 일이 아니다. **자산(대출채권)이 생기고 부채
(고객 예금)가 생기는 하나의 사건**이다.

```
DEBIT   대출채권      (자산 증가)
CREDIT  고객 예금     (부채 증가)
```

집행계좌는 이 분개에 등장하지 않는다. 그런데 지금 구조는 대출 실행을 집행계좌에서
고객계좌로의 **이체**로 처리하고 있어, 실행할 때마다 집행계좌 잔액이 줄어든다.
자금부가 계속 채워 넣어야 하는 구조인데 그것은 대출 실행의 회계가 아니다.

**이 결정은 ②에서 세운 결제 경로를 뒤집지 않는다.** 실제 자금이 오가는 거래 —
상환·자동이체·역분개 환급 — 는 `/api/v1/internal/payments` 를 그대로 쓴다.
**`LOAN_DISBURSE` 만** 의미에 맞는 별도 거래 경계로 분리한다.

| 거래 | 성격 | 경로 |
|---|---|---|
| 대출 실행 | 신용 창조 — 채권과 예금이 동시에 생긴다 | 별도 회계 거래 |
| 상환·자동이체 | 실제 자금이동 — 고객 예금이 은행으로 온다 | 내부 결제 |
| 역분개 환급 | 실제 자금이동 | 내부 결제 |

경로가 갈려도 **인가·FDS·멱등·감사·원장은 공통으로 지난다**(원칙 3). 갈리는 것은
회계적 의미이지 통제가 아니다.

### 6. `auth_token_id` 의 의미를 되돌린다

경계가 분리되면 `X-Auth-Token-Id` 는 **고객 인증을 증명하는 기술 식별자**라는
원래 의미를 그대로 유지한다. internal 경로는 이 헤더를 요구하지 않으므로
loan 이 가짜 값을 만들어 낼 이유가 사라진다.

### 7. Core Banking 의 internal API 는 전부 인증을 요구한다

> **최종 보안 모델은 모든 Core Banking internal API 에 인증을 요구한다. 단, 호출 주체에
> 따라 서비스 신원과 직원 신원을 구분한다. 서비스 간 호출은 credential 기반 service
> principal + operation permission 으로 인가하고, 직원 운영 작업은 직원 identity +
> RBAC/step-up 으로 인가한다.**

```
Gateway 의 외부 인증
      ↓
Core Banking 의 서비스·직원 주체 인증      ← 여기가 비어 있었다
      ↓
작업별 인가
      ↓
감사
```

`payment/config/SecurityConfig` 는 `anyRequest().permitAll()` 이고 그 주석은
"게이트웨이가 JWT 인증 → 백엔드는 통과" 다. 서비스 간 호출은 게이트웨이를 지나지
않으므로 이 전제가 성립하지 않는다(원칙 1·2).

**`/v1/internal/reconciliation/run` 은 직원 운영 경로로 본다.** 호출자 코드가 0건이라
사람이 부르는 것으로 보이고, 확인되지 않은 호출자를 위해 `OPERATOR` 라는 서비스
신원을 만들면 그 신원이 곧 우회로가 된다. 서비스가 아닌 것을 서비스로 등록하지 않는다.

#### 전환 절차

현재 무인증 호출을 즉시 차단하지 않는다. 승인 게이트를 켤 때 경로 목록을 사람이
주석에 적고 켰다가 여신 넷을 빠뜨린 일이 있었다(§문제 정의). 같은 실수를 반복하지
않으려면 목록을 **데이터로** 확인해야 한다.

```
1  발판    /v1/internal/** 에서 신원을 세우되 거절하지 않는다.
           미인증 호출만 감사에 남겨 누가 인증 없이 들어오는지 확인한다.
2  배선    확인된 호출자에게 신원과 작업 권한을 부여하고 자격증명을 보내게 한다.
3  강제    미인증 호출이 0 이 된 것을 확인한 뒤 거절로 전환한다.
4  방지    internal 컨트롤러가 인가 없이 추가되는 것을 잡는 테스트를 둔다.
```

> **1단계의 allow 는 최종 보안 정책이 아니라 전환 절차다.**
> 이 문장을 적어 두는 이유는, 임시 허용이 아무도 고치지 않는 채로 정책이 되는 일이
> 흔하기 때문이다. 설정 이름(`enforce`)과 기본값이 그 상태를 드러내야 한다.

확인된 호출자와 필요한 작업 권한:

| 경로 | 호출자 | 주체 | 필요한 것 |
|---|---|---|---|
| `POST /v1/internal/payments` | loan-service | 서비스 | ✅ 이미 있음 |
| `POST /v1/internal/loan-disbursements` | loan-service | 서비스 | ✅ 이미 있음 |
| `GET /v1/internal/ledger/loan-summary` | loan-service | 서비스 | ✅ 이미 있음 |
| `GET /v1/internal/payments/{id}` | fds-detector | 서비스 | 신원 + `PAYMENT_DETAIL_READ` |
| `GET /v1/internal/banking/**` | agents/consultation | 서비스 | 신원 (인가는 A2 의 `ResourceAccessGuard` 가 이미 한다) |
| `POST /v1/internal/reconciliation/run` | 사람 | 직원 | 직원 인증 + RBAC |

> `/v1/internal/banking/**` 을 "무인증" 이라고 적었던 것은 부정확했다. A2 가 세운
> `ResourceAccessGuard` 가 행위자를 세우고 자원 접근을 판정한다 — **직원 인가는
> 있고 서비스 인증이 없다.** 두 주체 모델이 겹치는 자리이므로, 이 경로에 필요한
> 것은 작업 권한이 아니라 호출한 서비스의 신원이다.

## 이 결정이 하지 않는 것

- **서비스 인증의 전송 수단을 정하지 않는다.** 현재는 `X-Internal-Token` 이 그 자리를
  맡고 있고, 제대로 하려면 mTLS 다 —
  [`security-zone-topology.md`](security-zone-topology.md) 의 "서비스 간 호출" 참조.
  이 문서는 그 위에 얹는 **인가 계층**을 정한다.
- **기존 고객 경로를 바꾸지 않는다.** `/api/v1/payments` 와 `TransferApprovalGate` 는
  그대로다.
- **권한 부여 화면을 만들지 않는다.** 레지스트리는 마이그레이션으로 심고, 운영 화면은
  필요해질 때 별도로 정한다.

## 적용 범위

이번 구현은 `Loan → Payment` 에서 시작하지만 **payment 국소 보안 패치가 아니다.**
같은 인가 모델을 이후 서비스 간 호출 전반에 적용한다.

```
Loan     → Payment      이번 구현
Deposit  → Customer     승인 검증 등
Agent    → Core Banking A2 가 만드는 internal 읽기 경로
FDS      → Core Banking 조회
```

### 도메인은 분리하고, 메커니즘만 공통화한다

```
                    CORE BANKING
                         │
          ┌──────────────┼──────────────┐
          │              │              │
       Deposit         Payment         Loan
          │              │              │
     own policy      own policy      own policy
          │              │              │
          └──────────────┼──────────────┘
                         │
                common authorization
                    mechanism
```

| 무엇 | 어디 |
|---|---|
| 인가 판정 코드·작업 어휘·판정 결과 모델 | **`common/`** — 한 벌 |
| 권한 레지스트리 데이터와 정책 값 | **각 도메인 스키마** — 도메인마다 |

**공통화하는 것은 보안 원칙과 메커니즘이지 정책이 아니다.** 어떤 서비스에 무엇을
허용할지는 그 자원을 가진 도메인이 정한다. 반대로 하면 — 정책을 한 곳에 모으면 —
도메인 경계가 인가 테이블을 통해 다시 얽힌다.

## 지금 상태와의 거리

| 항목 | 상태 |
|---|---|
| `/api/internal/**` + `ROLE_INTERNAL` 패턴 | 있음 — loan(`SecurityConfig:117`), fds, auto-loan-review |
| `X-Internal-Token` 서비스 인증 | 있음 (전송 수준) |
| Payment 의 internal 결제 엔드포인트 | **없음** — 만들어야 한다 |
| 작업 단위 인가(operation permission) | **없음** — 역할만 있고 작업 어휘가 없다 |
| 거래 정책(금액·계좌·거래종류) | **없음** |
| internal 경로 감사 | **없음** — A2/B1 이 세운 `deposit_access_log` 는 조회 감사다 |
| 여신 자금이동이 실제로 도는가 | **아니오** — 401 로 막혀 있다 |

## 검증

이 결정이 지켜지는지 기계가 볼 수 있어야 한다. 같은 종류의 누락이 또 나지 않도록,
**"게이트를 지나는 경로 목록" 을 사람이 주석에 적지 않고 코드에서 도출한다.**

- 자금이동 컨트롤러를 열거해, 고객 경로는 승인 게이트를 지나고 internal 경로는
  서비스 인가를 지나는지 확인하는 테스트
- internal 경로가 `FdsPreCheckGate` 를 건너뛰지 않는지 확인하는 테스트
