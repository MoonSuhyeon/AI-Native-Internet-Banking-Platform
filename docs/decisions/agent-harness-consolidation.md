# 에이전트 하네스 통합 — 설계 결정 기록

## 문제 정의

에이전트가 7개인데 **실행 골격이 도메인마다 따로 있다.**

| 에이전트 | 언어 | LLM | 루프 | 관측 |
|---|---|---|---|---|
| review-ai-gateway | Java | Claude | 자체 AgenticLoop | Langfuse |
| auto-loan-review | Java | Gemini (OpenAI 호환) | 자체 루프 | Langfuse (별도 구현) |
| advisory-service | Java | — | — | 없음 |
| doc-agent | Java | — | — | 없음 |
| fraud-investigation-agent | Python | 자체 | LangGraph | 자체 tracing.py |
| consultation | Python | 자체 | 없음 | 부분 |
| goal-agent | Python | 자체 | 없음 | 부분 |

에이전트가 실제로 해야 하는 일은 도메인이 달라도 같은 모양이다.

```
1 고객 조회 → 2 신용정보 조회 → 3 RAG 검색 → 4 계산 → 5 Tool 호출
→ 6 출력 검증 → 7 로그 저장 → 8 Trace 저장 → 9 실패 시 Retry → 10 승인 후 응답
```

이 열 단계를 처음부터 끝까지 통과하는 경로는 현재 **없다.** 가장 근접한 대출심사조차
1·2가 빠져 있고, 관측은 Langfuse 하나뿐이며, 검증 게이트는 근거 검증 한 종류다.

### 왜 이렇게 됐나 — core-banking 과 같은 원인

[core-banking-merge](core-banking-merge.md) 에서 확인한 것과 같은 구조다.
대출 담당이 auto-loan-review 를, 사기 담당이 fraud-investigation 을, 상품 담당이
consultation 을 각자 만들었다. **경계가 요구사항이 아니라 담당자 분담을 따라 그어졌고,**
그 결과 도메인 지식이 전혀 없는 부품(추적·감사·재시도)까지 사람 수만큼 복제됐다.

## 실측 결과 — 짐작이 두 번 틀렸다

계획을 세우기 전에 실제로 셌다. 두 번 다 짐작과 달랐고, 그때마다 계획이 바뀌었다.

### 1) "Python 이 작으니 그쪽을 재작성하면 된다" → 틀림

| | 파일 | 총 줄수 | 파일당 |
|---|---|---|---|
| Java | 340 | 19,979 | 58 |
| Python | 57 | 19,307 | 338 |

파일 수는 4:1 이지만 **코드량은 사실상 반반이다.** 파일 수 차이는 언어 문화(Java 는
DTO·enum 을 파일 하나씩 쪼갠다)일 뿐이었다.

따라서 "한 런타임으로 통일" 안을 배제하는 근거는 "한쪽이 작다"가 아니라
**"양쪽 다 크고, 통일하면 Python ML 생태계(LangGraph·평가 하네스)를 버리게 된다"** 이다.

### 2) "6·7·8·9 가 3벌씩 중복이다" → 틀림

| 단계 | 실제 |
|---|---|
| **8 Trace** | **진짜 중복.** Java 2벌(128줄·98줄, 공개 API 거의 동일) + Python 1벌(64줄) |
| **7 감사** | **중복 아님.** auto-loan-review 에만 12파일, 나머지 5개 전부 0 |
| **9 재시도** | 편차. auto 5 / gateway 2 / goal 1 / consultation·fraud **0** |
| **6 검증** | 다 있으나 검증 대상이 제각각 (26 / 6 / 14 / 2 / 5 파일) |

**중복 제거 작업이 아니라 확산 작업이었다.** 감사 로그가 대출심사에만 있다는 것은
상담 챗봇이 고객에게 무엇을 답했는지 남는 기록이 없다는 뜻이다. 컴플라이언스 관점에서
이쪽이 중복보다 큰 문제다.

## 결정

### 목표는 "모든 요청이 흐르는 하나의 파이프라인"이 아니다

대출심사·사기조사·상담은 하는 일이 다르다. 한 실행 경로에 밀어넣으면
`if (도메인 == 대출)` 분기 덩어리가 되고, 그것은 통합이 아니라 뒤엉킴이다.

**파이프라인 정의는 하나, 인스턴스는 도메인마다 둔다.**
열 단계의 순서와 각 단계의 계약(입출력·검증 방식·기록 형식)이 고정되고,
그 안을 채우는 내용물만 도메인별로 다르다.

### 무엇을 합치고 무엇을 두는가

기준은 하나다 — **도메인 지식이 들어가는가.**

| 단계 | 도메인 지식 | 하네스 소유 |
|---|---|---|
| 6 출력 검증 | 없음 (스키마·근거·주입저항) | ✅ 전부 |
| 7 로그 저장 | 없음 (감사 불변성) | ✅ 전부 |
| 8 Trace 저장 | 없음 | ✅ 전부 |
| 9 Retry | 없음 (백오프·상한·비용) | ✅ 전부 |
| 3 RAG 검색 | 기법은 공통, 인덱스는 도메인별 | ✅ 인터페이스만 |
| 5 Tool 호출 | 규약은 공통, 툴은 도메인별 | ✅ 레지스트리만 |
| 10 승인 | 정책이 도메인별(여신 4-eye, 챗봇 없음) | ✅ 게이트 추상, 정책 주입 |
| 1·2 컨텍스트 수집 | 도메인별 | ❌ 인터페이스만 |
| 4 계산 | 도메인 그 자체 | ❌ |

### 새로 만드는 것이 아니라 꺼내는 것이다

Java 쪽에는 부품이 이미 있다. 흩어져 있을 뿐이다.

```
AuditImmutabilityEnforcer   감사 불변성
LlmCostMeter                비용 상한
LlmRequestRateMeter         레이트 제한
PiiAwareChatClient          PII 마스킹
AgentLoopGuard              폭주 방지
GroundingValidator          근거 검증
```

## 순서 — 실측 결과로 재조정됨

원래 "6·7·9 를 함께 추출"로 묶었으나, 셋의 성격이 완전히 다르다는 것이 실측으로 드러났다.
6은 도메인 분리가 필요하고, 7은 확산이며, 9는 신규 개발이다.

### 1. Trace 를 OpenTelemetry 로 (먼저)

유일하게 순수 중복이고 도메인 결합이 없다. 지금은 Langfuse 에 직결돼 있어 다른 도구를
붙일 수 없다. OTel 을 표준 인터페이스로 두고 Langfuse·Phoenix 를 exporter 로 뺀다.

**이것이 먼저인 이유**: 통합 전후를 같은 자로 비교할 수 있게 된다. 이게 없으면
"합쳤더니 나아졌다"를 증명할 수 없다.

**완료 기준**: 3개 하네스의 trace 가 한 대시보드에서 같은 스키마로 보인다.

### 2. 감사를 harness-core 로 (앞당김)

없는 곳에 생기는 이득이 가장 크다. 원래 6·9와 묶여 있었으나 분리해 앞으로 옮긴다.

**완료 기준**: 5개 에이전트가 같은 감사 기록 형식을 쓴다.

### 3. 재시도 정책 신규 개발

현재 `AgentLoopGuard` 는 **폭주 방지(상한)** 이지 재시도가 아니다. 백오프·재시도 상한·
비용 연동을 새로 만든다.

### 4. 출력 검증 (뒤로 미룸)

`GroundingValidator` 198줄이 도메인에 얽혀 있다.

```
com.bank.ai.agent.AgentOpinion   ← 대출 심사 의견 타입
com.bank.ai.rule.domain          ← 여신 규칙
com.bank.ai.rag.policy           ← 정책 인용
```

"근거 없는 주장을 걸러낸다"는 일반 로직과 "AgentOpinion 을 검증한다"는 대출 전용 로직이
섞여 있어 그대로 꺼낼 수 없다. 가장 어렵다.

### 5. 두 번째 언어로 검증

`fraud-investigation-agent`(Python)를 같은 계약으로 옮긴다.
**한 언어에서만 되는 것은 계약이 아니다.** 여기서 어긋나면 앞 단계 설계가 틀린 것이고,
그것을 아는 것도 성과다.

### 6. 입력단·계산 연결 (별도 과제)

1·2(고객·CB 조회), 4(계산). 현재는 loan-service 가 대신 조회해 넘겨주는 구조라,
에이전트가 스스로 컨텍스트를 모으게 할지가 설계 결정이다. 위 단계들과 성격이 다르다.

## 예상되는 한계

- **1~3단계는 화면에 보이지 않는다.** 기능이 늘지 않는다. 산출물은 이 문서와
  "왜 6·7·8·9만 합치고 1·2·4는 두는가"라는 판단 자체다.
- **5단계에서 추상이 깨질 수 있다.** Java 기준으로 뽑은 계약이 Python 에 맞지 않을
  가능성이 실재한다. 그러면 2~4단계를 다시 해야 한다.
- **일정 추정은 신뢰하지 않는다.** core-banking 병합도 "테스트 몇 개"로 보였다가
  마이그레이션 체인이 처음부터 깨져 있는 것을 발견했다. 여기도 열어보면 나온다.

### 1단계에서 실제로 얻은 것

- `harness.tracing.endpoint` 하나로 Langfuse ↔ Phoenix ↔ Jaeger 가 바뀐다. 코드 변경이 없다.
- LLM 호출을 `gen_ai.*` 시맨틱 규약으로 기록한다. 자체 필드명을 쓰면 도구마다 매핑을
  다시 해야 하지만, 표준이면 어느 도구든 같은 필드로 읽는다.
- 추적에 싣는 입출력은 4,000자로 자른다. 프롬프트 전문을 실으면 추적 백엔드가 로그
  저장소가 되고 비용이 터진다. 전문은 보존기간·불변성을 책임지는 감사 로그에 남는다.

### 2단계에서 배운 것 — NoOp 은 선택이 아니다

감사를 끄면 빈이 사라져 의존하는 쪽(드리프트·공정성 테스트)이 깨졌다. 추적에는
`NoOpAgentTracer` 를 뒀으면서 감사에는 두지 않은 설계 불일치였다.
**기능을 끄는 것이 의존하는 쪽을 깨뜨리면 안 된다.**

또 하나 — H2 판별은 제품명이 아니라 URL 로 해야 한다.
`MODE=PostgreSQL` 로 띄운 H2 는 제품명이 PostgreSQL 로 보고돼 트리거 검증에 걸린다.

### 3단계에서 구분한 것 — 루프 가드와 재시도는 다른 축이다

- `AgentLoopGuard`: 한 실행 <b>안에서</b> 툴·LLM 을 몇 번까지 부를 수 있는가 (폭주 방지)
- `RetryPolicy`: 한 번의 호출이 실패했을 때 몇 번까지 다시 시도하는가 (복구)

기존에는 앞의 것만 있었고 재시도는 for 문으로 흩어져 있었다. 흩어진 구현에는
`retryable` 판단과 비용 연동이 없어, 다시 해도 같은 결과인 실패를 비싸게 반복했다.

## 4단계 사전 분석 — GroundingValidator 를 어디서 자를 것인가

198줄이 두 종류로 갈린다. 이 경계가 4단계 작업의 전부다.

**하네스로 갈 부분 (도메인 지식 없음)**

| 대상 | 성격 |
|---|---|
| `resolveExists(id)` | 인용된 근거가 실제로 존재하는지 확인. 환각 방지의 핵심 |
| `INLINE_PREFIX` / `RAG_PREFIX` | 인용 식별자 규약 |
| `ValidationResult` | 검증 결과 표현 |

**대출에 남을 부분**

| 대상 | 왜 남는가 |
|---|---|
| `validate(ReviewReport)` | 심사 리포트 구조를 안다 |
| `validateNumericClaims(AgentOpinion, TrackDecision)` | 여신 판단 타입에 묶여 있다 |
| `MIN_CITATIONS_TRACK_2 = 2` | TRACK_2 정책 상수 |

정리하면 **"인용이 실존하는가"는 뽑고 "심사 의견이 규칙과 맞는가"는 남긴다.**
`PolicyIndex` 를 하네스가 인터페이스로 정의하고 도메인이 구현하는 형태가 된다.

## 4단계 결과

경계는 분석대로 그었다. 이름만 바꿨다 — 하네스 쪽은 `PolicyIndex` 가 아니라
`CitationIndex` 다. "정책"은 대출 어휘라 하네스에 들어오면 사기·상담이 쓸 수 없다.
도메인의 `PolicyIndex` 가 이를 상속하고, 정책 <b>본문</b>을 다루는 `get` 만 도메인에 남는다.

| 위치 | 내용 |
|---|---|
| `harness.validation.CitationIndex` | 실존 확인 계약 (메서드 하나) |
| `harness.validation.CitationResolver` | `inline:` / `rag:` prefix 규약과 라우팅 |
| `harness.validation.ValidationResult` | 검증 결과 어휘 |
| `GroundingValidator` (대출) | 198줄 → 158줄. 리포트 구조·여신 타입·Track 2 하한만 남음 |

### 통합 테스트를 먼저 붙인 것이 실제로 값을 했다

기존 `GroundingValidatorTest` 는 인덱스를 손으로 만들어 주입하는 단위 테스트라
**배선이 끊겨도 통과한다.** 실제 Spring 컨텍스트로 도는 `GroundingWiringIntegrationTest`
8건을 리팩터링 <b>전</b> 코드에서 통과시켜 기준선을 만들고, 옮긴 뒤 같은 8건으로 확인했다.

그중 하나는 규칙 자체를 지키는 테스트다 — **RAG 를 끈 환경에서 `rag:` 인용은 차단되어야 한다.**
여기가 열려 있으면 RAG 를 끄는 것이 검증을 끄는 일이 된다. 인덱스가 없을 때
"확인할 수 없음"을 통과로 처리하는 것은 흔한 실수고, 끄고 돌리는 환경에서만 드러난다.

### `rag:` 인용 비율 계측이 prefix 를 다시 알아야 했다

도메인이 RAG 인용 수를 세는데, 그러려면 prefix 문자열을 알아야 한다. 규약이 하네스로
갔는데 도메인이 문자열을 다시 비교하면 규약이 두 군데로 흩어진다.
`CitationResolver.isRagCitation()` 을 두어 규약이 한 곳에만 있게 했다.

## 2-d 진행 상황 — 계약은 섰고 배포가 남았다

`agents/harness-core/python/harness_core` 에 계약 모듈을 두었다.
상세와 사용법은 [그 README](../../agents/harness-core/python/README.md).

**계약(`audit.py`)과 저장 구현(`audit_sqlalchemy.py`)을 나눴다.** 조사하다 나온 제약이다 —
`fraud-investigation-agent` 에는 DB 의존성이 아예 없다(`langgraph`·`httpx` 뿐).
계약에 SQLAlchemy 를 넣으면 그 에이전트는 감사를 붙이려고 DB 드라이버를 얹어야 하고,
그러면 "가벼운 에이전트는 감사를 안 붙인다"가 된다. 그게 애초의 문제였다.

### 전달 방식 — 빌드 컨텍스트를 올렸다 (복사본을 만들지 않았다)

Python 에이전트의 빌드 컨텍스트가 각자의 디렉터리여서
(`context: agents/consultation`, `COPY app/ ./app/`) 공유 패키지가 이미지에 들어가지
않았다. 컨텍스트를 `agents/` 로 올리고 Dockerfile 이 `harness-core/python/harness_core`
를 함께 COPY 한다.

에이전트마다 복사본을 두는 안을 쓰지 않은 이유가 핵심이다 —
**테스트가 대조하는 파일과 이미지에 들어가는 파일이 달라진다.**
`test_audit_contract.py` 는 레포의 파일을 읽으므로, 사본을 두면 대조가 초록인데
컨테이너 안 계약은 다를 수 있다. 감사 로그에서 그 어긋남은 사후 조사하려고 기록을
꺼낼 때에야 드러난다. 가장 늦게 아는 형태다.

대가는 컨텍스트 크기다. `agents/` 461MB 중 451MB 가 Java 빌드 산출물이라
`agents/.dockerignore` 가 없으면 빌드마다 그것을 전송한다.
**실측 결과 전송량 514KB** — 이 파일이 A 안의 전제 조건이다.

### 상담 챗봇 배선 — 부재 문제의 실체가 메워졌다

`handle_message` 가 커밋한 뒤 응답을 조립하기 직전에 감사를 남긴다.
`output_json` 에 **고객에게 실제로 나간 문장**이 들어간다. 그게 이 기록의 존재 이유다.

실제 PostgreSQL 로 확인한 것 (Java 쪽 2-b 와 같은 기준):
기록·되읽기(한글 보존)·`trace_id` 연결·JSONB 기본값 보정·UPDATE/DELETE 트리거 차단.

### 검증되지 않은 채 남은 것

consultation 의 기존 테스트 스위트는 **이 환경에서 원래 돌지 않는다**
(`langfuse` 미설치, `CONSULTATION_DATABASE_URL` 필수). 내 변경 이전부터 그렇다.
그래서 배선 검증은 의존성이 갖춰진 이미지 안에서 했다. 상담 테스트가 로컬에서
도는 상태로 만드는 것은 별도 과제다.

### goal-agent

같은 계약으로 배선했다. 기록 지점은 `run_goal_agent` — Claude 경로와 mock 경로가
합류하는 유일한 자리다. 각 경로 안에서 남기면 한쪽을 고칠 때 다른 쪽을 빠뜨린다.

API 키가 없어 mock 으로 답한 경우를 `fallback_reason="LLM_KEY_ABSENT_MOCK"` 으로 남긴다.
이것이 없으면 나중에 기록을 봤을 때 모델의 판단과 고정 응답을 구별할 수 없다.

테이블은 `init_db.py` 가 만든다. SQLAlchemy 모델로 표현하지 않은 이유는
INSERT-ONLY 트리거가 계약의 일부인데 모델로는 표현되지 않기 때문이다.

빌드 컨텍스트가 바뀌어 `docker build agents/goal-agent` 는 더 이상 동작하지 않는다.
README 를 고쳤다 (원래 적혀 있던 `docker compose up goal-agent` 도 틀린 것이었다 —
goal-agent 는 어느 compose 에도 등록돼 있지 않다).

## 5단계 — fraud 를 계약 위로: 계약은 섰고, 구멍 두 개가 드러났다

**한 언어에서만 되는 것은 계약이 아니다**를 확인하는 단계였다. 결론부터:
계약의 <b>모양</b>은 성립했고, <b>범위</b>에 빠진 것이 두 가지 있었다.

배선은 실제로 돈다. 사건 하나를 끝까지 돌려 확인했다.

```
사건: case_death
남은 감사 기록: 2 건
  agent=fraud-investigation subject=FRAUD_CASE/ALT-DEATH phase=RECOMMENDATION  도구호출=1
  agent=fraud-investigation subject=FRAUD_CASE/ALT-DEATH phase=ACTION_EXECUTION 승인자역할=['FRAUD_OFFICER']
권고 status 보존: FAIL_CLOSED
첫 도구: get_party | 이유: 권리자 적격성(사망·후견)은 결정적이라 먼저 확인 — 맞으면 즉시 fail-closed
```

도구 선택 이유가 그대로 남는 것이 특히 중요하다. 사기조사에서는 결론보다
**어떤 도구를 왜 그 순서로 불렀는가**가 더 자주 문제가 된다. 조사 경로가 편향돼
있으면 결론이 옳아 보여도 근거가 없기 때문이다.

### 성립한 것

- `subject_type` + `subject_id` 문자열 쌍이 그대로 맞았다 (`FRAUD_CASE` / alert id).
  도메인 컬럼을 두지 않은 판단이 두 번째 도메인에서 값을 했다.
- `tool_calls_json` 이 fraud 의 `tool_log` 와 모양이 같았다. 맞춘 적이 없는데 맞았다.
- 저장 구현이 하나 더 필요했지만(`audit_psycopg`) **이것은 계약이 깨진 것이 아니다.**
  저장 방식은 계약이 아니다. 어떤 필드를 어떤 테이블에 남기는가가 계약이고 그것은 같다.

### 구멍 1 — 행위자 필드가 없었다 (메움)

fraud 는 지급정지·STR 을 <b>사람 승인 뒤에</b> 실행한다. 그런데 스키마에
누가 승인했는지 넣을 자리가 없다. 지금은 `output_json` 안에 `actor_roles` 를 넣어
기록만은 남게 했지만, 이러면 "이 사람이 무엇을 승인했는가"를 에이전트를 가로질러
물을 수 없고 에이전트마다 이름이 달라질 수 있다.

**행위자는 도메인 지식이 아니다.** 사람 승인을 받는 에이전트라면 어디서나 있다.
대출심사에서 안 드러난 이유는 그쪽 승인 기록이 loan-service 쪽 별도 감사에 있어서다.
지급정지를 걸 수 있는 에이전트에서 "누가 승인했는가"는 부수 정보가 아니라 감사의 핵심이다.

### 구멍 2 — 한 대상에 판단이 하나라고 가정했다 (메움)

fraud 는 한 사건에 기록이 둘이다(권고 / 실행). 둘을 합칠 수 없다 —
사이에 사람이 있고 거기서 거부될 수 있다. 권고만 남기면 "실제로 지급정지가 걸렸나"를,
실행만 남기면 "무슨 근거로 그랬나"를 알 수 없다.

계약은 이것을 <b>담기는</b> 한다. 그러나 `find_latest(subject_type, subject_id)` 는
`recorded_at DESC` 로 하나만 돌려주므로 항상 실행 기록이 나오고,
**"이 사건의 권고를 다오"를 물을 방법이 없다.** 지금은 `output_json.phase` 로 구분하고
있는데, 그건 규약이 아니라 내가 이번에 정한 관례다.

## 6단계 — 계약 확장: 두 구멍을 컬럼으로 올렸다

`decision_kind`·`actor_id`·`actor_roles` 를 스키마에 추가했다.
셋 다 도메인 지식이 없고, 셋 다 JSON 안에 숨어 있으면 질의할 수 없다.

### 확인된 것 (실제 PostgreSQL)

```
=== '이 사건의 권고를 다오' 가 답해지는가 ===
  종류 안 좁히면       : ACTION_EXECUTION   ← 항상 마지막 기록 (구멍 그 자체)
  RECOMMENDATION 요청  : RECOMMENDATION     ← 이제 답해진다
=== 행위자가 컬럼으로 질의되는가 ===
  RECOMMENDATION     actor_id=None       roles=[]              ← 사람 개입 전
  ACTION_EXECUTION   actor_id=emp-9001   roles=['FRAUD_OFFICER']
  'emp-9001 이 승인한 건수' 질의: 1 건
```

마지막 줄이 actor 를 컬럼으로 올린 이유다. payload 안에 있으면 이 질의가 불가능하다.

**자율 판단은 `actor_id` 가 NULL 로 남는다.** 빈 값이 아니라 사실이다 —
사람이 개입하지 않았다는 뜻이고, 나중에 "이 판단에 사람이 있었나"를 그 NULL 로 답한다.

### 사본 갱신에서 배운 것 — 확장은 CREATE 로 못 간다

정본만 고치면 <b>이미 만들어진 테이블에는 컬럼이 안 생긴다.</b>
`CREATE TABLE IF NOT EXISTS` 는 기존 테이블을 만나면 통째로 건너뛴다.
그래서 정본에 멱등 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 를 함께 넣었다.
신규 DB 는 CREATE 로, 기존 DB 는 ALTER 로 같은 모양이 된다.

auto-loan-review 는 **V8 을 고치지 않고 V9 를 새로 냈다.** 적용된 마이그레이션을
수정하면 Flyway 체크섬이 어긋나 기동이 실패한다 — 이 레포에서 이미 겪은 실패다.
V8 적용 상태의 DB 에 V9 를 얹어 12컬럼 → 15컬럼이 되는 것을 실제로 확인했다.

그 결과 대조 테스트도 바뀌어야 했다. 한 에이전트의 유효 스키마가 **여러 파일을
순서대로 적용한 결과**가 되었기 때문이다. 첫 파일만 보면 확장을 놓치고
"사본이 원본과 다르다"는 잘못된 실패가 난다. `_effective_columns` 가 CREATE 에
ALTER 를 덧붙여 계산한다.

### 대조 테스트가 값을 했다

확장 도중 실제로 두 번 잡혔다.

1. Java 컴포넌트를 `actorRolesJson` 으로 지었는데 컬럼은 `actor_roles` 였다.
   이름이 다르면 계약이 아니다 — 테스트가 인덱스 13에서 잡았다.
2. ALTER 파서가 세미콜론을 타입에 포함해 `VARCHAR(64);` 로 읽었다.

둘 다 손으로 봤으면 놓쳤을 종류다.

### 구멍은 아니지만 대가였던 것 — 전달 방식이 에이전트마다 달랐다

| 에이전트 | harness_core 전달 |
|---|---|
| consultation | Docker 빌드 컨텍스트 (`agents/`) |
| goal-agent | Docker 빌드 컨텍스트 (`agents/`) |
| fraud | **Dockerfile 이 없다** — `pytest.ini` 의 pythonpath + 런타임 PYTHONPATH |

fraud 를 배선하자 패키지 import 가 통째로 깨졌다(테스트 4개 파일 수집 실패).
2-d 에서 고른 안이 세 번째 에이전트에 그대로 적용되지 않는다는 뜻이다.
계약의 문제는 아니지만, "공유 패키지를 어떻게 전달하는가"에 아직 단일한 답이 없다.
현재 상태는 fraud 40건 통과.

## 7단계 — 행위자를 채우려다 인가 우회를 발견했다

계약에 `actor_id` 자리를 만들었으니 채우기만 하면 되는 줄 알았다. 실제로는
**fraud 서비스에 인증이 아예 없다**는 것을 여기서 알게 됐다.

### 두 번 틀렸다

**첫 번째 — 클라이언트가 신원을 보내게 하려 했다.**
`ApproveRequest` 에 `actor_id` 를 추가했다. 그러나 승인 기록의 신원을 클라이언트가
자칭하면 위조할 수 있고, 위조 가능한 신원은 NULL 보다 나쁘다 — 비어 있는 게 아니라
**채워진 것처럼 보이기** 때문이다. 레포 관례도 이미 이걸 피하고 있었다
(게이트웨이가 JWT 에서 `X-Employee-Id` 주입, 클라이언트는 직원 ID 를 보내지 않음).

**두 번째 — 헤더로 바꾸면 되는 줄 알았다.**
사이드카가 `X-Employee-Id` 를 믿게 고쳤는데, 사이드카는 8090 으로 브라우저에
직접 열려 있었다. 게이트웨이를 우회해 헤더를 손으로 붙이면 그만이다.
**체크박스로 위조하던 것이 헤더로 위조하는 것으로 형태만 바뀌었고,
감사 기록만 더 믿음직해 보이게 됐다.** 바로 앞 문단에서 비판한 실패를 그대로 저질렀다.

### 실제로 있던 구멍은 감사가 아니라 인가였다

`asFraudOfficer` 는 화면의 체크박스였다. 그 값이 그대로 RBAC 게이트를 통과해
지급정지·STR 발동을 결정하고 있었다. 감사에 누가 승인했는지 안 남는 것보다
**권한 없는 요청이 승인을 통과하는 것**이 더 심각한 문제였는데, 후자를 찾으려고
전자를 파다가 발견했다.

(동작은 전부 목이라 실제로 움직인 자금은 없다. 그러나 목을 실물로 바꾸는 순간
그대로 뚫린다.)

### 세 가지가 한 세트여야 성립한다

하나라도 빠지면 "게이트웨이가 주입한 신원이라 믿는다"는 전제가 무너진다.
특히 1·2만 하고 3이 빠지면 아무것도 안 한 것보다 위험하다 —
공격 표면은 그대로인데 팀은 해결됐다고 여기게 된다.

| | 내용 |
|---|---|
| 1 | 프론트가 사이드카 직접 호출을 버리고 게이트웨이 경유 (`/api/v1/internal/fraud/**`) |
| 2 | 게이트웨이 라우트 + JWT→헤더 주입 |
| 3 | **사이드카를 호스트에서 닿지 못하게** (compose `internal` 네트워크, `ports` 없음) |
| 4 | `effective_roles` 의 본문 fallback 제거 — 같은 배포에 함께 |

4를 미루면 네트워크를 막아도 자칭 역할을 신뢰하는 경로가 코드에 남는다.
설정 실수 하나로 다시 뚫리는 "죽었지만 살아있는" 경로다.

### 2는 이미 되어 있었다

`JwtAuthenticationFilter` 가 클라이언트발 `X-Employee-Id`·`X-User-Role` 을
**먼저 제거한 뒤** JWT 클레임으로 주입하고 있었다. 라우트만 추가하면 됐다.
기존 인프라가 맞게 되어 있는데 새 서비스가 그 바깥에 있었던 것이 문제였다.

### 3이 가장 컸다 — fraud 는 컨테이너가 아니었다

`ports` 를 지우라는 조언은 적용할 수 없었다. **fraud 는 Dockerfile 도 compose
서비스도 없었다.** 호스트에서 `uvicorn 0.0.0.0:8090` 으로 도는 프로세스라
Docker 네트워크 정책이 닿지 않는 곳에 있었다.

2-d 에서 "fraud 는 Dockerfile 이 없어 빌드 컨텍스트 안이 적용 안 된다"고 적었던
것과 **같은 뿌리**다. 컨테이너화가 안 돼 있으면 컨테이너 기반 대책이 전부 비껴간다.

그래서 Dockerfile 을 새로 만들고 compose 서비스로 넣었다. 네트워크는
**`fraud-internal` 하나만 새로 두고 거기 붙는 것은 fraud-agent 와 api-gateway 둘뿐이다.**
전면 internal/external 개편을 하지 않은 것은 의도적이다 — 나머지 20여 개 서비스의
토폴로지를 건드리면 되돌리기 어려워지고, 지금 필요한 격리는 한 서비스에만 필요하다.

로컬에서 8090 을 직접 찔러야 하는 개발자는 `docker-compose.override.yml` 로
자기 환경에만 연다(`.sample` 제공, git 제외). 운영 compose 는 안전한 채로 남는다.

### 결과 (실측)

| 상황 | 이전 | 지금 |
|---|---|---|
| 헤더 위조 (시크릿 미설정) | `FREEZE_PAYMENT` 실행됨 | **거부됨(RBAC)** |
| 헤더 위조 (시크릿 불일치) | 실행됨 | **거부됨(RBAC)** |
| 게이트웨이 경유 | — | 실행 + `actor_id=emp-9001` |

검증된 신원만 `actor_id`·`actor_roles` **컬럼**에 들어간다. 자칭 역할은
`claimed_roles` 로 `request_json` 에 따로 남는다 — 기록은 남기되 컬럼과 섞지 않는다.
섞으면 읽는 사람이 검증된 것과 자칭한 것을 구별할 수 없고, 컬럼 전체의 신뢰도가
자칭 수준으로 떨어진다.

`FRAUD_GATEWAY_SHARED_SECRET` 은 **미설정이 기본이고 그때 헤더를 전혀 믿지 않는다**
(fail-closed). 다만 이것은 네트워크 격리의 대체재가 아니라 최소 방어선이다.

### 남은 부담 하나 — 이제 테스트가 지킨다

`harness_audit_log` 마이그레이션이 harness-core 원본과 각 에이전트 DB 에 <b>복사본으로</b>

생기면 사라질 부담이다.

손으로 맞춰야 하는 상태를 없애지는 못했지만 **어긋나면 테스트가 먼저 알리는 상태**로는 바꿨다.
`test_audit_contract.py` 가 원본 SQL·사본 SQL·Java record·Python dataclass 넷을
파일에서 직접 읽어 대조한다. 컬럼 이름만 비교하면 `VARCHAR(64)` → `VARCHAR(16)` 같은
변경을 놓치고 그 드리프트는 감사 기록을 <b>조용히 잘라서</b> 저장하는 형태로 나타나므로,
이름·타입·순서를 함께 본다. 네 종류(누락·추가·순서·타입)를 실제로 어긋뜨려 탐지되는지
확인했다.
