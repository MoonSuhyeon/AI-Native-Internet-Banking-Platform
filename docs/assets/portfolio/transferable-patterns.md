# 도메인을 옮겨도 남는 것 — 이 레포에서 재사용 가능한 구현

> 이 레포는 은행 업무를 구현했지만, **은행이라서 필요한 것**과 **자유도 높은
> 시스템이면 어디서나 필요한 것**이 섞여 있다. 이 문서는 뒤쪽만 골라 정리한다.
>
> 판정 기준은 하나다: **"규제가 은행이 아니어도 같은 문제가 생기는가."**
> 예금 이자 계산은 안 남고, "에이전트가 볼 수 있는 범위를 값으로 만든다" 는 남는다.

---

## 1. 에이전트 하네스 — `agents/harness-core`

두 런타임(Java·Python)이 같은 규칙을 구현하도록 만든 공용 계층. 에이전트를 쓰는
어떤 도메인에도 그대로 옮겨진다.

### 1-1. 관측 기본값을 뒤집기 — `tracing.py`

Langfuse·LangSmith 계열의 `@observe` 는 **함수 인자와 반환값을 자동으로 싣는다.**
계측을 켜는 순간 추적 저장소가 입력 데이터의 사본이 된다.

여기서는 기본값을 뒤집었다. **아무것도 자동으로 싣지 않고**, 실을 것을
`update_current_span()` 으로 명시한다.

```python
with span("plan_next_tool", kind="LLM"):
    update_current_span(tool=chosen, reason=reason)   # 실을 것만
```

- **옮겨지는 곳**: 의료·법률·인사·고객지원 — 프롬프트에 민감 정보가 들어가는 모든 곳
- **왜 남는가**: 관측 도구의 기본값이 "다 담기" 인 것은 벤더 공통이다. 도메인이
  바뀌어도 그 기본값은 그대로다

### 1-2. 지우지 말고 가명처리 — `pii.py`

두 함수가 성격이 다르다.

| 함수 | 대상 | 왜 따로인가 |
|---|---|---|
| `mask_text` | 자유 텍스트에 섞여 든 것 | 정규식으로 잡는다 |
| `pseudonymize` | **필드 자체가 식별자**인 것 | `customer_id="9111"` 은 정규식이 못 잡는다 |

지우지 않고 가명처리하는 이유: **`[MASKED]` 로 지우면 "같은 사람의 건 3개" 를 묶을
수 없다.** HMAC 이면 묶을 수는 있고 되돌릴 수는 없다.

소금이 없으면 프로세스마다 가명이 달라진다 — 미설정 시 **임의 값으로 시작해 그
사실이 드러나게** 했다. 빈 소금으로 고정하면 무지개표에 뚫린다.

- **옮겨지는 곳**: 사용자 ID·환자 ID·직원 번호를 다루는 모든 파이프라인
- **왜 남는가**: "익명화하면 분석이 안 되고, 안 하면 유출된다" 는 트레이드오프가
  도메인 독립이다

## 2. 에이전트가 볼 수 있는 범위를 **값**으로 만들기

`agents/fraud-investigation-agent/src/agent/scope.py`

문제는 이렇게 생긴 한 줄이었다.

```python
ident = state.alert.account if tool in ACCOUNT_TOOLS else state.alert.customer_id
```

이 줄이 **두 파일에 각각** 있었다. 지금 값은 맞다. 다만 그것은 *규칙이 강제돼서*가
아니라 *두 줄이 우연히 같아서*다. 그 차이는 이럴 때 드러난다.

- 도구 호출을 진짜 tool-calling 으로 바꾸면(모델이 인자까지 만든다) 이 줄이
  사라지고, 사라져도 **아무 테스트가 실패하지 않는다**
- 한쪽 루프만 고치면 다른 쪽은 조용히 예전 규칙으로 남는다

그래서 호출부가 식별자를 *넘기는* 대신 스코프에게 *물어본다*.

```python
subject = scope.subject_for(tool)     # 넘길 수 없으면 잘못 넘길 수도 없다
```

- **옮겨지는 곳**: 멀티테넌트 SaaS(테넌트 격리), 사내 지식 에이전트(부서별 열람 범위),
  개인화 추천(다른 사용자 데이터 접근)
- **왜 남는가**: `do`(무엇을 할 수 있나)는 RBAC·HITL 이 잡는데, **`see`(무엇을 볼 수
  있나)를 잡는 장치는 대부분 없다.** 이 구멍은 도메인 무관하다

## 3. LLM 심판 없는 결정적 평가

`agents/fraud-investigation-agent/src/agent/evaluation.py`

표준 방식은 gpt-4o 같은 모델에게 "이 선택이 타당했나" 를 묻는 것이다. 두 가지가 걸린다.

1. **심판에 넘기는 것이 곧 데이터다.** 외부로 나가는 경로가 하나 더 생긴다
2. **같은 입력에 같은 점수가 안 나오면 감사에서 설명할 수 없다**

대신 `tool_matrix.py` 가 "도구마다 어떤 시나리오 쌍을 가르는지" 를 결정적으로 적어
두었으므로, **"그 시점에 무엇이 경합 중이었나" 와 대조**하면 채점이 된다.

채점 항목 셋이 서로 다른 실패를 잡는다.

| 함수 | 잡는 실패 |
|---|---|
| `score_tool_choice` | 예산을 판별에 썼나, 흘렸나 (6단계 verdict) |
| `fail_closed_respected` | 결정적 사실이 나온 뒤에 더 뒤졌나 |
| `score_investigation` | 위 둘을 건당으로 묶은 값 |

**한계도 적어 뒀다**: 매트릭스가 정답지이므로 매트릭스가 틀리면 채점도 틀린다.
이 채점은 "플래너가 적힌 분별력을 활용했나" 만 본다.

- **옮겨지는 곳**: 도구 선택이 있는 모든 에이전트 — 코드 어시스턴트, 리서치 에이전트,
  운영 자동화
- **왜 남는가**: LLM-as-judge 의 두 약점(데이터 유출·비결정성)은 도메인과 무관하다.
  **정답지를 만들 수 있는 문제라면 심판을 쓸 이유가 없다**

## 4. 불변식을 테스트로 못 박기 — `common/src/test/.../monitoring/`

이 레포에서 반복해 만난 실패는 하나였다. **컴파일되고, 렌더링되고, 테스트가 통과하는데
아무 일도 안 하는 코드.** 눈으로는 안 보인다. 그래서 "이건 이래야 한다" 를 테스트로
적었다.

| 테스트 | 무엇이 무너지면 잡히나 | 실제로 잡은 것 |
|---|---|---|
| `FrontendGatewayOnlyTest` | 프론트가 서비스를 직접 부름 | 클라이언트 8개가 게이트웨이를 우회 → 신원 헤더가 안 붙어 **인가가 통째로 무의미** |
| `GatewayRouteCoverageTest` | 프론트가 부르는 경로에 라우트 없음 | `/api/v1/banking/**` 무라우트 — 화면은 멀쩡하고 목록만 늘 비어 보임 |
| `ApiSpecFreshnessTest` | 문서가 없는 서비스를 소개 | 병합된 서비스 3종 + 존재한 적 없는 1종, 엔드포인트 91개 누락 |
| `PlanStatusTest` | 계획서가 상태를 안 밝힘 | 33건 중 2건이 코드와 반대로 적혀 있었음 |
| `SidecarExposureTest` | 사이드카 호스트 포트 노출 | 게이트웨이 우회 경로 |
| `ComposeNetworkReachabilityTest` | 망 격리가 풀림 | — |
| `DockerBuildContextTest` | 빌드 컨텍스트 누락 | 에이전트 이미지 빌드 실패 |
| `EntitySchemaConsistencyTest` | 엔티티 ↔ 마이그레이션 어긋남 | `auth_token` 테이블 부재 → **승인 토큰 발급이 항상 500**, 소액 초과 이체 전면 불가 |
| `ThemeTokenSyncTest` | 색 토큰 두 벌이 어긋남 | — |

### 이 계열이 도메인 독립인 이유

위 아홉 개 중 은행이라서 필요한 것은 **하나도 없다.** 전부 "선언한 규약과 실제가
어긋나는데 아무도 모른다" 는 같은 문제다.

### 함께 옮겨야 하는 것 — 빌드 입력 선언

이 레포에서 **다섯 번** 겪은 함정이다. 검사가 읽는 파일을 빌드 태스크 입력으로
선언하지 않으면 Gradle 이 `UP-TO-DATE` 로 건너뛴다. **지키라고 만든 검사가 조용히
안 도는 상태**가 되고, 규칙을 깨는 변경이 그대로 통과한다.

```gradle
tasks.named('test') {
    inputs.files(rootProject.fileTree('.') {
        include 'docs/api-spec.md'                 // 검사가 읽는 문서
        include 'services/*/src/main/java/**/*Controller.java'
    })
}
```

## 5. 변이 검증 — 규칙을 깨서 테스트가 우는지 본다

이 레포의 작업 규약이다. 규칙을 하나 만들면 **그 규칙을 무력화해 보고 테스트가
깨지는 것을 확인한 뒤 되돌린다.**

```
가드 삭제 → 테스트 4건 FAILED → 복원
라우트 삭제 → 테스트 3건 FAILED → 복원
날짜 필터 무력화 → 테스트 5건 FAILED → 복원
```

**왜 필요한가**: "테스트가 통과한다" 는 "테스트가 무언가를 지킨다" 와 다르다. 실제로
이 레포에서 복식부기 검증 여섯 곳이 **변수를 자기 자신과 비교**하고 있었다. 전부
통과했고, 아무것도 안 지키고 있었다.

- **옮겨지는 곳**: 전부. 도구도 언어도 필요 없다

## 6. 사람과 AI 사이의 통제 구조

### 6-1. 격리에는 나오는 길이 있어야 한다

AI 감사 에이전트가 편향·위반을 의심하면 리포트를 `QUARANTINE` 으로 건다.
**들어가는 길만 있고 나오는 길이 없었다** — 관리자 화면에 버튼 셋이 있었지만 아무
데도 연결돼 있지 않아 영구 격리였다.

처분은 상태만 바꾸지 않는다. **격리를 푼 사실 자체가 감사 대상**이라, 누가·언제·왜를
남기지 않으면 통제가 아니라 그냥 상태 변경이다. DB CHECK 로도 강제한다.

```sql
CHECK (quarantine_disposition_cd IS NULL
       OR (quarantine_disposed_at IS NOT NULL
           AND quarantine_disposed_by IS NOT NULL
           AND length(btrim(quarantine_disposition_note)) > 0))
```

처분 셋 중 **정상 판정만 격리를 끝낸다.** 재심사·조사 의뢰는 아직 열린 사안이라
`RESOLVED` 로 바꾸면 목록에서 사라지고 아무도 다시 안 본다.

- **옮겨지는 곳**: 콘텐츠 모더레이션, 사기 탐지, 이상 트래픽 차단 — **자동 차단이
  있는 모든 곳**
- **왜 남는가**: "AI 가 건 것을 사람이 풀 수 있는가" 는 자동화가 있으면 항상 생긴다

### 6-2. 채택률 — "AI 가 잘 도는가" 와 "사람이 받아들였는가" 는 다르다

`ReviewAdoptionMetrics`

기존 AI 지표는 전부 시스템 지표(지연·비용·실패율)라 **"사람이 AI 를 받아들였는가"** 를
답할 수 없다. AI 권고 방향과 사람의 최종 결정을 대조해 ADOPTED/REJECTED 를 센다.

권고가 없는 트랙(`TRACK_3` 사람 심사 필수)은 **집계에서 제외**한다 — 넣으면 분모가
부풀어 채택률이 낮아 보인다.

사람→사람 축(4-eye 번복)도 따로 센다. AI→사람 축과 섞으면 어느 쪽이 문제인지 모른다.

- **옮겨지는 곳**: 추천 시스템, 코드 리뷰 봇, 자동 분류 — **사람이 최종 결정하는 모든 AI**
- **왜 남는가**: AI 도입 성과를 묻는 질문은 도메인 무관하고, 시스템 지표로는 답이 안 된다

## 7. 신원은 게이트웨이가 정한다

호출자가 적은 값을 절대 믿지 않는다. 게이트웨이가 JWT 를 검증해 **같은 이름의 헤더를
지우고 덮어쓴다**(`X-Customer-Id`·`X-Employee-Id`·`X-User-Role`).

이 규약이 무너진 실제 사례들:

| 무너진 방식 | 결과 |
|---|---|
| 상담 서비스에 라우트가 없어 브라우저가 직접 호출 | 코드·주석은 "JWT 에서 추출해 사칭 방지" 라고 말했지만 **토큰이 도착한 적이 없었다** |
| 프록시가 `Authorization` 을 버림 | 인가를 붙인 뒤 관리자 화면이 전부 거절됨 |
| 요청 본문의 `customer_no` 를 신뢰 | 남의 고객번호를 적으면 **그 사람 계좌에서 돈이 나갔다** |
| 계약 해지에 소유자 검증 없음 | 유효한 토큰만 있으면 **남의 예적금을 해지** 가능 |

`FrontendGatewayOnlyTest` + `GatewayRouteCoverageTest` 두 개가 이 규약을 지킨다.

- **옮겨지는 곳**: 게이트웨이 뒤에 서비스를 두는 모든 구조
- **왜 남는가**: "신원을 누가 정하는가" 를 한 곳으로 몰지 않으면 반드시 한 곳이 샌다

## 8. 도메인 규칙은 엔티티에, 서비스에 두지 않는다

서비스에 두면 **새 호출 경로가 검사를 건너뛴다.**

```java
// 금액 없는 단축이체는 목록에 보이지만 보낼 수 없다.
// 등록 경로가 나중에 하나 더 생겨도(가져오기·배치) 같은 검사를 지난다.
public static void assertAmountMatchesType(FavoriteType type, Long amount) { ... }
```

같은 규칙을 **DB CHECK 로도 적는다.** 애플리케이션을 우회하는 경로(수동 SQL·다른
서비스)가 있기 때문이다.

- **옮겨지는 곳**: 전부
- **왜 남는가**: "지금은 호출부가 하나뿐" 이라는 전제는 시간이 지나면 항상 깨진다

## 9. 문서를 생성물로 만들기

`docs/api-spec.md` 첫 줄은 "소스 컨트롤러에서 자동 추출" 이라고 말했는데
**추출기가 레포에 없었다.** 손으로 관리되니 서비스 병합을 못 따라갔고, 결국
**문서를 보고 붙이면 없는 서비스를 부르는** 상태가 됐다(엔드포인트 91개도 누락).

문서를 한 번 더 손으로 맞추면 다음 병합 때 또 어긋난다. **뽑는 방법 자체를 남기고**
(`scripts/extract_api_spec.py --check`) 테스트로 못 박았다.

계획 문서도 같다. 33건의 완료 표시가 제각각(`- [x]` · ✅ · 머리말 · 없음)이라
구분이 안 됐고, **둘은 코드와 반대로 적혀 있었다.** 상태 어휘를 넷으로 못 박고
형식만 테스트한다 — **상태가 사실인지는 일부러 검사하지 않는다.** 기계가 판정하려
들면 거짓 경보가 난다.

- **옮겨지는 곳**: API 문서·아키텍처 다이어그램·의존성 목록 — 손으로 관리되는 모든 것
- **왜 남는가**: "문서가 낡는다" 는 문제는 문서를 고쳐서 풀리지 않는다
