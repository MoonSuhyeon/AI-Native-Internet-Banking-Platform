# 이체 거래 승인 인증(step-up) 설계 노트

작성 배경: 계정계·인증보안계 점검에서 나온 6건 중 마지막 항목. 나머지 다섯은 코드로
고쳤고, 이것만 두 도메인에 걸쳐 있어 설계부터 적는다.

## 지금 상태 (확인한 사실)

- `POST /api/transactions/transfer` 의 요청 DTO(`TransferRequest`)에 인증수단 관련 필드가
  **없다.** 서비스도 확인하지 않는다. 소유권 검증은 이번에 넣었으므로 "본인 계좌에서만
  나간다"는 보장되지만, **로그인 세션만 있으면 추가 확인 없이 금액 제한까지 이체된다.**
- 인증보안계에 있는 인증수단은 **로그인 용도만** 구현돼 있다 — PIN 로그인
  (`POST /api/v1/auth/pin-login`), 인증서 로그인(`/api/v1/auth/cert-login`), QR.
- 보안카드는 **에러 코드만 있고 구현이 없다.** `CustomerErrorCode` 에
  CUST_140~143(활성 보안카드 없음 / 중복 / 코드 불일치 / **챌린지 만료**)까지 정의돼 있는데
  이 코드를 던지는 코드가 없다. 챌린지-응답 흐름까지 설계됐다가 멈춘 흔적이다.

즉 **이체 API 가 부를 대상이 애초에 없다.** 수신계가 연동을 빠뜨린 것이 아니라,
인증보안계가 거래 승인용 인증수단을 아직 내놓지 않은 상태다.

## 왜 필요한가

실물 은행에서 이체는 로그인과 다른 등급의 행위다. 로그인은 "누구인가"를 묻고, 이체는
"지금 이 금액을 이 계좌로 보내는 것이 맞는가"를 묻는다. 세션이 탈취됐을 때 마지막으로
남는 방어선이 이것이라, 로그인 인증만으로 이체가 되면 세션 하나가 곧 자금 유출이다.

## 설계 — 거래 승인 토큰

인증수단 검증은 인증보안계에 두고, 계정계는 **토큰 한 장만 확인**한다. 계정계가 PIN·인증서
같은 비밀을 직접 다루지 않게 하는 것이 핵심이다.

```
1. 고객이 이체 화면에서 확인을 누른다
2. 프론트 → 인증보안계: 인증수단 검증 요청 (PIN·인증서·보안카드 응답)
                        + 이 이체의 내용(출금계좌·수취계좌·금액)
3. 인증보안계: 검증 성공 시 거래 승인 토큰 발급
                - 짧은 유효기간(예: 3분)
                - 1회용(사용 즉시 소멸)
                - **거래 내용에 바인딩** — 금액·계좌가 다르면 무효
4. 프론트 → 계정계: 이체 요청 + 승인 토큰
5. 계정계: 인증보안계에 토큰 검증 요청 → 성공해야 이체 실행
```

**거래 내용 바인딩이 빠지면 의미가 없다.** 토큰이 "이 사람이 인증했다"만 뜻하면, 1,000원
이체로 받은 토큰으로 1,000만원을 보낼 수 있다. 토큰은 "이 사람이 *이 이체를* 승인했다"를
뜻해야 한다.

### 계약 (초안)

인증보안계가 내부 API 두 개를 낸다.

```
POST /api/v1/internal/transaction-approvals
  요청  { fromAccountId, toAccountNo, amount, authMethod, credential }
  응답  { approvalToken, expiresAt }
  실패  CUST_142(코드 불일치) / CUST_143(챌린지 만료) 등 기존 코드 재사용

POST /api/v1/internal/transaction-approvals/verify
  요청  { approvalToken, fromAccountId, toAccountNo, amount }
  응답  { valid: true }            ← 검증 성공 시 토큰 소멸
  실패  401 (없음·만료·이미 사용·거래 내용 불일치)
```

계정계는 `TransferRequest` 에 `approvalToken` 을 추가하고, 이체 전에 verify 를 부른다.

### 단계적 도입

한 번에 다 하면 프론트·챗봇까지 같이 멈춘다. 순서를 나눈다.

| 단계 | 내용 | 도메인 |
|---|---|---|
| 1 | 승인 토큰 발급·검증 API 구현 (PIN 부터. 보안카드는 그다음) | 인증보안계 |
| 2 | `TransferRequest.approvalToken` **선택 필드**로 추가 + 있으면 검증 | 계정계 |
| 3 | 웹·챗봇 이체 흐름에서 토큰 발급 단계 추가 | 프론트·상담 |
| 4 | 토큰 **필수**로 전환 (설정 스위치로 켜고, 로그로 미사용 호출 확인 후) | 계정계 |

4단계를 설정으로 켜는 이유는, 필수로 바꾸는 순간 토큰을 안 보내는 경로가 전부 죽기
때문이다. 미사용 호출이 0 인 것을 로그로 확인한 뒤 켠다.

## 결정이 필요한 것

- **어느 인증수단을 이체 승인에 쓸 것인가.** PIN 만으로 갈지, 금액 구간별로 나눌지
  (예: 100만원 초과는 인증서). 실물 은행은 금액·수취인 등록 여부로 나눈다.
- **보안카드를 살릴 것인가.** 에러 코드가 이미 있으니 챌린지-응답을 구현하면 되지만,
  요즘 은행은 보안카드를 줄이는 추세다. 데모 목적이면 PIN + 인증서로 충분할 수 있다.
- **면제 범위.** 본인 명의 계좌 간 이체, 소액(예: 5만원 이하)까지 매번 물을지.

## 이번 점검에서 이 항목의 책임 소재

처음에는 "인증수단은 있는데 이체 API 가 안 부른다"로 보고 인증보안계 몫을 30% 로 봤다.
확인해 보니 **거래 승인용 인증수단 자체가 없다.** 수신계는 부를 대상이 없었으므로,
이 항목은 인증보안계 몫이 더 크다 — 60~70% 로 본다.
