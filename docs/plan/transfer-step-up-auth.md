# 이체 거래 승인 인증(step-up) 설계 노트

작성 배경: 계정계·인증보안계 점검에서 나온 6건 중 마지막 항목. 나머지 다섯은 코드로
고쳤고, 이것만 두 도메인에 걸쳐 있어 설계부터 적는다.

## 지금 상태 (확인한 사실)

**인증수단은 갖춰져 있다.** 인증서 체계가 종류 구분까지 포함해 구현돼 있다.

| 있는 것 | 위치 |
|---|---|
| 인증서 발급 — `CERT_COMMON`(공동) / `CERT_FIN`(금융) / `CERT_AXFUL` | `POST /api/v1/auth/cert/issue` |
| 종류별 PIN 규칙 — 금융인증서 6자리 숫자, 공동인증서 8~30자 | `CertIssueRequest` |
| 인증서 PIN 검증 + 잠금·만료·폐기 판정 + 실패 누적 FDS 평가 | `CertLoginService.certLogin` |
| 인증서 관리 — 목록·상세·폐기·PIN 변경 | `/api/v1/cert/manage/**` |
| QR 인증서 승인 흐름 (generate / status / approve) | `/api/v1/auth/qr-cert/**` |
| PIN 로그인 | `POST /api/v1/auth/pin-login` |
| 인증수단 관리 — 목록·별칭·대표 지정·삭제 | `/api/v1/customers/me/auth-methods` |

**없는 것은 인증수단이 아니라 거래 승인용 출구다.** 위 검증들은 결과가 전부
**로그인 토큰**으로 나간다. "이 사람이 맞다"까지는 확인하지만 "이 사람이 *이 이체를*
승인했다"를 표현하는 응답이 없다.

그래서 계정계 쪽은 이렇게 남아 있다.

- `POST /api/transactions/transfer` 의 `TransferRequest` 에 인증수단 관련 필드가 없고
  서비스도 확인하지 않는다. 소유권 검증은 이번에 넣었으므로 "본인 계좌에서만 나간다"는
  보장되지만, **로그인 세션만 있으면 추가 확인 없이 한도까지 이체된다.**

보안카드는 별개로, 실제로 구현이 없다. `CustomerErrorCode` 에 CUST_140~143(활성 보안카드
없음 / 중복 / 코드 불일치 / **챌린지 만료**)까지 정의돼 있는데 이 코드를 던지는 코드가
없다. 챌린지-응답까지 설계됐다가 멈춘 흔적이다.

## 왜 필요한가

실물 은행에서 이체는 로그인과 다른 등급의 행위다. 로그인은 "누구인가"를 묻고, 이체는
"지금 이 금액을 이 계좌로 보내는 것이 맞는가"를 묻는다. 세션이 탈취됐을 때 마지막으로
남는 방어선이 이것이라, 로그인 인증만으로 이체가 되면 세션 하나가 곧 자금 유출이다.

## 설계 — 거래 승인 토큰

인증수단 검증은 인증보안계에 두고, 계정계는 **토큰 한 장만 확인**한다. 계정계가 PIN·인증서
같은 비밀을 직접 다루지 않게 하는 것이 핵심이다.

```
1. 고객이 이체 화면에서 확인을 누른다
2. 프론트 → 인증보안계: 인증서 PIN 검증 요청
                        + 이 이체의 내용(출금계좌·수취계좌·금액)
3. 인증보안계: 검증 성공 시 거래 승인 토큰 발급
                - 짧은 유효기간(예: 3분)
                - 1회용(사용 즉시 소멸)
                - **거래 내용에 바인딩** — 금액·계좌가 다르면 무효
4. 프론트 → 계정계: 이체 요청 + 승인 토큰
5. 계정계: 인증보안계에 토큰 검증 요청 → 성공해야 이체 실행
```

**거래 내용 바인딩이 빠지면 의미가 없다.** 토큰이 "이 사람이 인증했다"만 뜻하면, 1,000원
이체로 받은 토큰으로 1,000만원을 보낼 수 있다. 토큰은 "이 사람이 *이 이체를* 승인했다"를
뜻해야 한다.

### 새로 만들 것은 검증이 아니라 출구다

`CertLoginService.certLogin` 안에 필요한 판정이 이미 다 들어 있다 —
인증서 조회 → 잠금·폐기·만료 검사 → PIN 대조(`certPinHash`, 없으면 credential 해시로 폴백)
→ 실패 시 `recordLoginFailure` + 인증서 사용 이력 저장 + FDS 평가.

이 블록을 `verifyCertPin(serialNumber, pin, ip)` 같은 메서드로 뽑아 두 곳에서 쓴다.

```
certLogin            → verifyCertPin → 로그인 토큰 발급      (기존)
approveTransaction   → verifyCertPin → 거래 승인 토큰 발급   (신규)
```

즉 인증 로직을 새로 짜는 작업이 아니라 **같은 검증의 결과를 다른 형태로 내보내는**
작업이다. 실패 처리·잠금·FDS 가 자동으로 따라오는 것도 이 방식의 이점이다.

### 계약 (초안)

인증보안계가 내부 API 두 개를 낸다.

```
POST /api/v1/internal/transaction-approvals
  요청  { fromAccountId, toAccountNo, amount, certSerialNumber, pin }
  응답  { approvalToken, expiresAt }
  실패  CUST_031/032(폐기·만료) · CUST_033(PIN 불일치) · CUST_034(잠금) — 기존 코드 재사용

POST /api/v1/internal/transaction-approvals/verify
  요청  { approvalToken, fromAccountId, toAccountNo, amount }
  응답  { valid: true }            ← 검증 성공 시 토큰 소멸
  실패  401 (없음·만료·이미 사용·거래 내용 불일치)
```

계정계는 `TransferRequest` 에 `approvalToken` 을 추가하고, 이체 전에 verify 를 부른다.

### 단계적 도입

한 번에 다 하면 프론트·챗봇까지 같이 멈춘다. 순서를 나눈다.

| 단계 | 내용 | 도메인 | 크기 |
|---|---|---|---|
| 1 | `verifyCertPin` 추출 + 승인 토큰 발급·검증 API | 인증보안계 | 작음 (검증 재사용) |
| 2 | `TransferRequest.approvalToken` **선택 필드**로 추가 + 있으면 검증 | 계정계 | 작음 |
| 3 | 웹·챗봇 이체 흐름에 인증 단계 추가 | 프론트·상담 | 중간 |
| 4 | 토큰 **필수**로 전환 (설정 스위치로 켜고, 미사용 호출 0 확인 후) | 계정계 | 작음 |

4단계를 설정으로 켜는 이유는, 필수로 바꾸는 순간 토큰을 안 보내는 경로가 전부 죽기
때문이다. 미사용 호출이 0 인 것을 로그로 확인한 뒤 켠다.

## 결정이 필요한 것

- **금액 구간별 정책.** 인증서 종류가 이미 구분돼 있으므로(`CERT_FIN` / `CERT_COMMON`)
  "고액은 인증서, 소액은 PIN 로그인 재확인" 같은 정책을 바로 표현할 수 있다.
  실물 은행은 금액·수취인 등록 여부로 나눈다.
- **면제 범위.** 본인 명의 계좌 간 이체, 소액(예: 5만원 이하)까지 매번 물을지.
- **보안카드를 살릴 것인가.** 에러 코드가 이미 있어 챌린지-응답만 구현하면 되지만,
  요즘 은행은 보안카드를 줄이는 추세다. 인증서가 갖춰져 있으므로 없이도 성립한다.

## 이번 점검에서 이 항목의 책임 소재

추정이 두 번 움직였다. 근거가 바뀔 때마다 적는다.

| 시점 | 인증보안계 몫 | 근거 |
|---|---|---|
| 최초 | 30% | "인증수단은 있는데 이체 API 가 안 부른다"로 봄 |
| 중간 | 60~70% | 거래 승인용 인증수단 자체가 없다고 판단 — **틀렸다.** 보안카드만 보고 인증서를 빠뜨렸다 |
| 현재 | **35%** | 인증서는 완비. 없는 것은 거래 승인용 출구(API) 하나 |

최초 판단이 사실상 맞았다. 중간 추정은 보안카드 부재를 인증수단 전체의 부재로 잘못
읽은 결과다.

35% 로 보는 이유: 인증수단과 검증 로직은 인증보안계에 갖춰져 있으므로 "역할을 안 했다"는
아니다. 다만 거래 승인 출구를 내지 않았고, "이체는 로그인과 다른 등급의 인증이 필요하다"는
요구를 어느 문서에도 적지 않았다. 계약을 공급하는 쪽이 그 한계를 명시할 몫이 남는다.
나머지 65% 는 자금 이동 API 를 인증수단 없이 설계·구현한 쪽에 있다.
