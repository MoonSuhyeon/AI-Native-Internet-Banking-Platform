## 3-b. 자원 제한

`mem_limit` 을 넣었다. 넣기 전에는 **41개 컨테이너 전부 무제한**이었다.

무제한이 특히 나빴던 이유는 JVM 서비스가 `-XX:MaxRAMPercentage=75` 를 쓰기 때문이다.
이 설정은 **컨테이너 제한이 있을 때** 의미가 있는데, 제한이 없으면 "호스트 전체
메모리의 75%" 를 상한으로 본다. 안전장치처럼 보이지만 전제가 없어 사실상 아무것도
막지 않고 있었다.

값은 지어내지 않고 유도했다.

| 근거 | 예 |
|---|---|
| 이미 명시된 힙에서 | ES `-Xmx2g` → 3g (루씬 오프힙 포함) · doc-agent `-Xmx384m` → 512m |
| `MaxRAMPercentage=75` 역산 | 한도 1g → 힙 768m |
| 공식 권장 | kibana 1g |

실측으로 확인했다(customer-service 583MiB/1GiB, kafka 490MiB/1GiB, gateway 224MiB/768MiB
— 최고 57%).

| 남은 것 | 내용 |
|---|---|
| **CPU 제한 없음** | `cpus` 는 아직 안 걸었다. 메모리와 달리 넘치면 느려질 뿐 죽지는 않아 후순위 |
| **부하 시 검증 안 됨** | 기동 직후 값이다. 이체·심사를 돌리는 상태에서 다시 봐야 한다 |
| **1회성 잡은 제외** | `payment-topic-init`·`kafka-connect-init` — 초기화가 메모리로 막히면 스택 전체가 안 뜬다 |

프로파일별 상한 합계: 기본 18.5GB · `doc` +1.8 · `rag` +5.0 · `mock` +0.2

## 3-c. 은행 아키텍처 표준 대비 격차

외부 리뷰에서 받은 지적을 **레포에서 확인한 뒤** 정리했다. 지적 중 일부는 이미
구현돼 있었고, 일부는 전제가 달랐다. 아래는 확인 결과 실제로 비어 있는 것들이다.

### 지금 바로 새는 곳

| 항목 | 확인한 사실 |
|---|---|
| **외부 LLM 으로 나가는 PII** | `PiiMaskingUtil` 이 있는데 **RAG 색인·자문 의견에만** 걸려 있다. `GeminiOpenAiCompatLlmClient`(자동심사)와 상담의 OpenAI 경로에는 마스킹이 없다. 프롬프트에 실린 고객 정보가 그대로 나간다 |
| **Langfuse·Phoenix 추적 데이터** | 프롬프트·응답을 그대로 적재한다. 마스킹 지점이 없어 추적 저장소가 PII 사본이 된다 |
| **서비스 경계를 넘는 DB 접근** | `consultation-service` 가 `core-banking-db-a` 의 deposit 스키마를 직접 읽는다. database-per-service 위반이며, 스키마를 바꾸면 상담이 조용히 깨진다 |

### 데모 범위 밖이지만 실물 은행에는 있는 것

| 항목 | 현재 | 비고 |
|---|---|---|
| **배치·온라인 자원 격리** | 같은 JVM. `KftcSettlementBatchWorker`·`ScheduledPaymentWorker`·`OutboxPublisher` 가 온라인 트래픽과 스레드·힙을 공유 | 대용량 마감이 온라인 지연으로 직결 |
| **읽기 전용 대사 DB** | 없음. 대사가 운영 DB 를 직접 읽는다 | Read Replica 분리 필요 |
| **ISO 20022 전문 변환** | Kafka JSON 이벤트로 대체 | 실제 KFTC/BOK 연계는 표준 전문 |
| **HSM** | Vault(Transit)로 대체 | doc-agent 봉투암호화에만 적용 |
| **DR·원장 HA** | 없음. `core-banking-a/b` 는 HA 가 아니라 **타행 시연용** | |
| **WORM 스토리지** | `agent_audit_log` 에 UPDATE/DELETE 차단 트리거는 있으나, 그 외 감사 테이블(`customer_access_log` 등)에는 없다 | 트리거는 DB 관리자를 못 막는다 |

### 확인해 보니 이미 있던 것 — 지적이 맞지 않았다

- **"postgres ×6 을 한 클러스터로 공유"** → 사실이 아니다. DB 8개가 각각 **독립 컨테이너·독립 볼륨**이다.
- **"복식부기에 2PC 가 필요"** → 자행이체는 core-banking 병합으로 **단일 트랜잭션**이 됐다(2PC 불필요).
  타행은 본질적으로 비동기라 2PC 를 걸 대상이 아니다. 대신 대사가 그 역할을 한다.
- **"EAI/ESB 레이어 부재"** → Kafka + Schema Registry 가 그 역할이다. 현대 마이크로서비스는
  ESB 를 의도적으로 피하므로, 여기서 필요한 것은 레이어 신설이 아니라 **토픽 거버넌스**다.

### 우선순위

1. **LLM 경로 PII 마스킹** — 지금 실제로 외부로 나간다. 나머지는 규모·인프라 문제지만 이건 유출이다.
2. **상담 → core-banking DB 직접 접근 제거** — 서비스 경계 위반. API 로 바꾼다.
3. 나머지는 데모 범위를 넘어서므로 "안 한다" 가 아니라 **"왜 안 했는지"** 를 적어 두는 선에서 둔다.

| 납입현황·입금(적금) | 납입 이력 |
| 거래 메모 수정 · 해지 예상 명세 | |
| 상품 비교 화면 | 로직은 챗봇(`PRODUCT_COMPARE`)에만 있어 목록 화면에서 못 쓴다 |
| 이메일 상담 접수 | `ConsultModal` 이 안내만 하고 신청할 곳이 없다 |

**격리 해제가 나머지와 성격이 다르다.** 편의 기능이 아니라 통제의 구멍이다.

### 결정이 필요한 것

- **미구현 드롭다운 7개** — `전체서비스 ▾`·`GLOBAL ▾`·푸터 드롭다운 3. `<span>` 으로
  바꿔도 `▾` 가 남는 한 약속은 그대로다. 메뉴를 만들거나 통째로 빼야 한다.
- **마이데이터 영역** — `카드 한번에 불러오기`·`선불기관 등록`. 카드의 주 버튼이라
  지우면 카드가 빈 껍데기가 된다. 카드째 뺄지 결정 필요.

## 7. 금융 도메인 특수성 대비 격차

앞의 3-c 가 "은행 아키텍처 표준" 대비였다면, 여기는 **에이전트를 금융에 놓을 때
생기는 제약** 대비다. 항목마다 레포에서 확인한 현재 상태를 먼저 적었다.

> **전제.** 에이전트 설계의 출발점은 모델이 아니라 **"어떤 데이터가, 어디에 있고,
> 누가 관리하며, 어떤 권한이 필요한가"** 다. 아래는 그 네 질문에 지금 답할 수 없는
> 지점들이다.

### 7-1. 세션 스코프 — 지금 가장 큰 구멍

자유도 높은 에이전트는 **에이전트가 볼 수 있는 범위 자체를 세션에 묶어야** 한다.
워크플로우 에이전트(경로가 고정된 것)는 여기까지 필요 없지만, 조사 에이전트는
스스로 도구를 고르므로 해당된다.

> **✅ 해결.** 그리고 **처음 적은 내용에 과장이 있었다.** 아래에 실제 확인 결과를
> 남긴다 — 틀린 진단을 지우면 같은 오진을 반복한다.

### 처음 적었던 것과 실제

처음엔 *"플래너가 다른 고객번호를 넣으면 그대로 조회된다"* 고 적었다. **도달 불가능한
경로였다.** `plan_next_tool` 은 `{tool, reason}` 만 돌려주고, 식별자는 두 루프 모두
`state.alert` 에서 가져온다. 플래너가 대상을 지목할 방법이 없다.

### 그래도 남아 있던 것

값은 맞았지만 그것이 **규칙이 강제돼서가 아니라 두 줄이 우연히 같아서**였다.

```python
# graph.py 와 api.py 에 각각 한 줄씩
ident = state.alert.account if tool in ACCOUNT_TOOLS else state.alert.customer_id
```

이 차이가 드러나는 순간이 온다.

- 진짜 tool-calling 으로 바꾸면(모델이 인자까지 만든다) 이 줄이 없어지고,
  **없어져도 실패하는 테스트가 없었다**
- `tools.py` 함수들은 아무 식별자로나 부를 수 있다. `get_auth_events` 는 실연결 시
  내부 API 를 실제로 친다
- 한쪽 루프만 고치면 다른 쪽이 조용히 옛 규칙으로 남는다

### 한 일

`scope.py` 의 `CaseScope` 로 범위를 **값**으로 만들고, `tools.call_tool` 을 유일한
정상 경로로 뒀다. 호출부가 식별자를 *넘기는* 대신 스코프에게 *물어본다* — 넘길 수
없으면 잘못 넘길 수도 없다. 두 루프의 중복 계산도 같이 사라졌다.

거절은 `OutOfScopeError(PermissionError)` 다. 조회 실패(`ValueError`)와 구분한다 —
앞은 "없다" 이고 이쪽은 "봐서는 안 된다" 라서 감사에서 뜻이 다르다.

검증(`tests/test_scope.py` 12건)은 *"지금 다른 고객이 조회되나"* 를 묻지 않는다.
그건 전에도 아니었다. **범위를 벗어나려는 시도가 거절되는가**를 묻는다.
부러뜨려 확인 — 경계를 없애면 5건, 거절 전에 도구를 부르게 하면 1건이 실패한다.

### 7-2. 데이터 계층과 쓰기 권한

보안 등급 3계층을 에이전트 권한에 반영해야 한다. 존 구분은
[`decisions/security-zone-topology.md`](decisions/security-zone-topology.md) 에
`edge/app/data/agent/egress/lab` 로 적어 뒀지만, **그 존이 권한으로 이어지지 않는다.**

| 계층 | 무엇 | 에이전트 권한 | 지금 |
|---|---|---|---|
| **Core** (최고) | 원장·거래, 계좌 잔고, 고객 신상 | 사전 정의 API 만. 직접 권한 부여 어려움 | 구분 없음 |
| **Middle** (중간) | 데이터마트, 리포트, 리스크 지표 | **읽기만**, 쓰기 불가 | 데이터마트 계층 자체가 없다 |
| **DMZ** (낮음) | 웹, API 게이트웨이 | 통과 | 있음 |

| 항목 | 확인한 사실 |
|---|---|
| **읽기/쓰기 구분이 없다** | 에이전트가 부르는 internal API 에 읽기 전용 표시가 없다. 계층상 Middle 이어야 할 조회가 Core 와 같은 자격으로 나간다 |
| **데이터마트 계층 부재** | 분석·리포트용 계층이 없어 에이전트가 원장 DB 를 직접 읽는 경로밖에 없다 (3-c 의 "읽기 전용 대사 DB" 와 같은 뿌리) |

**할 일** — internal API 를 읽기/쓰기로 나누고 에이전트 자격증명에 읽기만 준다.
데이터마트는 범위가 크므로 지금은 **"왜 없는지"** 를 적는 선에서 둔다.

### 7-3. 고객 인증·동의 — 에이전트가 대신할 수 없는 것

에이전트는 **고객의 법적 행위를 대체할 수 없다.** 식별과 동의는 사람이 한다.

| 항목 | 확인한 사실 |
|---|---|
| **동의 기록이 없다** | `customer-service` 마이그레이션에 `consent` 계열 테이블이 없다. 신용정보법상 제3자 제공·활용 동의를 남길 자리가 없다 |
| **인간 승인은 있으나 "의도 확인" 이 없다** | 지급정지·STR 은 승인을 요구한다. 다만 승인 화면이 *무엇에 대한 승인인지* 를 원문 그대로 보여 주지 않는다. 고위험 API 에서 핵심은 승인 버튼이 아니라 **의도를 정확히 확인시키는 것**이다 |

**할 일** — 동의 이력 테이블(목적·범위·시점·철회)과, 승인 화면에 에이전트가 실행할
요청 원문을 그대로 노출한다.

### 7-4. 규제 문서 RAG — 조항 단위 근거

| 항목 | 확인한 사실 |
|---|---|
| **조항 ID 가 강제되지 않는다** | `ChunkBatchItem.metadata` 가 `Map<String,Object>` "corpus별 자유 스키마" 다. 출처는 `sourceId + chunkSeq` 뿐이라 **문서와 오프셋**은 알아도 *몇 조 몇 항*인지는 모른다 |
| **설계는 이미 있다** | `fraud-investigation-agent/corpus_registry.md` 에 티어·ID 체계(T1/T2-①/T3, `T2B-10` 형태)가 잡혀 있다. 인덱스가 그걸 안 쓰고 있을 뿐이다 |
| **출력측 정책 평가가 없다** | "이 답변이 규정을 어겼는가" 를 판정하는 지점이 없다. 입력측 검색만 있고 출력 검사가 없다 |

**할 일** — 청크 메타에 조항 ID·주제 태그를 **필수 필드로** 올리고, 답변에 근거
조항을 함께 반환한다. 그 다음에 출력측 정책 평가를 붙인다(근거 없이 평가만 붙이면
판정을 설명할 수 없다).

### 7-5. 외부 연계 — 만들 수 있는 범위의 경계

금융결제원(KFTC)은 중앙 허브이고 보안심사·인증서 발급·호출 한도를 통과해야 붙는다.
**에이전트가 오픈뱅킹을 직접 부르는 구조는 성립하지 않는다** — 인증서와 API 키는
백엔드가 쥐고, 에이전트는 백엔드에 요청해 일부만 수행한다.

| 항목 | 확인한 사실 |
|---|---|
| **게이트웨이에 속도제한이 없다** | `api-gateway/application.yml` 에 `RequestRateLimiter` 가 없다. 외부 연계는 인증·로깅·**속도제한** 셋이 한 벌인데 하나가 빠져 있다 |
| **인증서·키 보관** | Vault 는 doc-agent 봉투암호화에만 쓰인다. 대외 연계용 키 보관 경로가 따로 없다 |
| **범위 밖** | 실제 KFTC 보안심사·인증서 발급·표준 전문(ISO 20022)은 이 레포에서 만들 수 있는 것이 아니다. **모사 대상이 아니라 경계로 적어 둔다** |

**할 일** — 게이트웨이 속도제한 추가(레디스 기반). 나머지는 경계로 문서화한다.

### 7-6. 금융 텍스트 정규화

| 항목 | 확인한 사실 |
|---|---|
| **표 인식은 있다** | `doc-agent` 에 `TableOcrResponse`·`InferenceServerTableOcrClient` 가 있어 표 영역 탐지까지는 간다 |
| **행 단위 레코드화가 없다** | 표를 (항목·지표·값·단위·시점)으로 쪼개 적재하는 단계가 없다. 텍스트로만 남는다 |
| **텍스트/숫자 저장소가 안 나뉘어 있다** | 전부 벡터 스토어로 간다. 수치는 feature store 로 갈라 **벡터 검색 + 수치 조회를 결합한 질의**가 되어야 한다 |
| **단위 정규화 없음** | 원화 단위(억/천만), 금리·스프레드(% vs bp), 날짜, 배수 표기가 원문 그대로다 |

**할 일** — 단위 정규화가 먼저다. 정규화 없이 레코드화하면 잘못된 숫자를 구조화해서
저장하게 된다.

### 7-7. LLM 경로의 가명처리

3-c 에 적은 PII 마스킹과 같은 뿌리지만 **적용 지점이 다르다.**

| 대상 | 지금 | 필요 |
|---|---|---|
| 프롬프트 | `GeminiOpenAiCompatLlmClient`·상담 OpenAI 경로에 마스킹 없음 | 마스킹 |
| 추적 저장소 | Langfuse·Phoenix 가 원문 적재 | 가명처리 |
| 학습·로그 | 정책 없음 | 신용정보법상 **가명처리** 후 사용 |
| PII 접근 | `customer_access_log` 에 조회 이력은 남는다 | 유지 |

> **외부 LLM 사용 자체가 규제 위반이 될 수 있다.** 지금 구조는 그 전제 위에서
> "그래도 쓴다면 무엇을 갖춰야 하나" 를 다루는 것이고, 정식 경로는 내부 추론
> (`inference-server`)이다. 이 전제를 README·결정 문서에 적어 두지 않으면 구조를
> 오해하게 된다.

### 우선순위

1. **세션 스코프** — 지금 도구 인자가 열려 있다. 자유도 높은 에이전트에서 이건
   설계 결함이지 미구현이 아니다.
2. **LLM 경로 가명처리** — 3-c 1순위와 같다. 실제로 나간다.
3. **게이트웨이 속도제한** — 한 벌이어야 할 셋 중 하나가 빠져 있다.
4. **조항 ID 필수화** — 설계가 이미 있어 비용이 낮다.
5. **동의 이력·읽기전용 자격** — 스키마와 인증 체계를 같이 건드려야 해서 뒤로.
6. 데이터마트 계층·표 레코드화·대외 연계는 **범위 밖으로 적어 두는 선**에서 둔다.

Dockerfile·compose 정의가 전부 없었고 메인 클래스도 없었다. 그런데 패키지는
`com.bank.loan.advisory.*` 였고 loan-service 내부를 직접 import 했으며, loan-service 의
`AdvisoryFlywayConfig` 가 그 마이그레이션을 돌리려 하고 있었다(파일이 클래스패스에
없어 아무것도 실행되지 않았다). 별도 서비스가 아니라 **떼어 놓은 loan-service 코드**였다.

그 결과 조용히 죽어 있던 것들:

- `AdvisoryClient` 의 HTTP 호출은 늘 실패했고 빈 목록으로 삼켜졌다. 주석의
  "장애 시 fail-open" 은 장애가 아니라 상시 상태였다.
- 응답 타입도 어긋나 있었다(배열 기대 vs 감싼 객체). 서비스가 떠 있었어도 결과는 같다.
- 테스트 하네스의 advisory 스텁이 늘 빈 배열을 돌려줘 **CRITICAL 미확인 약정 차단
  (LOAN_201)이 한 번도 발화하지 않았다.** 전 테스트가 초록이었다.
- `review-ai-gateway` 의 `ADVISORY_BASE_URL` 도 존재한 적 없는 호스트를 가리켰다.

| 빌드 파일(`build.gradle`/`pom.xml`) | ❌ |
| Dockerfile · compose 서비스 정의 | ❌ |

그런데 **부르는 쪽은 있다.** `loan-service` 의 `AdvisoryClient` 가 `/api/advisory/reports`
를 호출하고, `review-ai-gateway` 도 `ADVISORY_BASE_URL` 을 본다. 주소도 서로 다르다
(`:8085` 대 `:8080`).

`AdvisoryClient` 주석은 "advisory-service 장애 시 빈 목록 반환(fail-open)" 이라고
말하지만, 이건 장애가 아니라 **상시 상태**다. 자문 리포트는 늘 비어 있고 심사는
그대로 진행된다. 조용히.

**먼저 정할 것**: 이 서비스를 빌드에 넣을 것인가, 아니면 호출부를 걷어낼 것인가.
정하기 전에는 권한 수정이 의미가 없다 — 돌지 않는 코드를 고치는 것이다.
